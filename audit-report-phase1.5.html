🎯 一句話結論
Director + Skill Check 嘅 architecture 冇 critical bug 或者致命限制。3 個真正 affect 體驗嘅嘢都係 prompt-iteration-fixable (D-01 Director 揀錯 skill_key 變成不公平擲骰、D-02 stale disposition 令 Director 評判越來越離地、D-03 Director 加咗 2s latency 但冇 UI feedback)。其他 9 個係 edge cases / future-proof 嘅嘢。

🟡3 個 Medium

D-01 Director 可能揀 schema 入面唔存在嘅 skill_key — 玩家擲骰永遠失敗 Med Logic
症狀：Director verdict require_skill_check 嘅 skill_key 字段係 free-form string。LLM 可能 hallucinate「口才」「魅力」之類嘅 skill，但 state schema 入面冇呢個 field。extractSkillValue() fallback 返 0 → 玩家擲 d20 + 0 + 0，幾乎肯定 fail。
後果：玩家想試「同教練爭辯」、「打交」呢類 skill-based action，由於擲骰嗰個 skill 喺 state 入面冇 — 永遠 failure / critical_failure → 整個 Skill Check 系統感覺「不公平」。
Fix（小 prompt tune + code guard, ~30 分鐘）：
(a) Director system prompt 加 explicit「skill_key 必須完全 match state schema fields list 入面其中一個 numeric key (bar / number / meter_with_label)」。Pass current schema fields list 入 prompt。
(b) Code guard：extractSkillValue 如果搵唔到 key，console.warn + fallback to median of all numeric fields in state (而唔係 0)。
D-02 Director 永遠用 initial disposition 評判 — 關係冇進展感 Med Logic
症狀：Director 收到 playthrough_character_states.disposition 嘅 current value。但我哋從來冇 auto-update — Narrator 嘅 update_state tool 只 touch top-level state，唔 touch playthrough_character_states table。所以 Director 永遠睇住 turn 1 嘅 initial disposition (e.g. linsiya.trust = 0)。
後果：玩家送 5 個禮物 + 講咗 10 句溫柔嘢，但 Director 仍然 reject「親林思雅」嘅 attempt，因為 disposition 仲喺 0。Player 感受唔到「關係 evolve 緊」— red lines 似乎永遠 hard。
Fix（Phase 1.5.3 嘅 core item，~半日 work）：
(a) Narrator 加第二個 tool update_character_disposition — input = array of {character_name, axis, delta}。
(b) System prompt 教 Narrator：each turn 如果玩家 action 影響任何 NPC 嘅 trust / romance / respect / fear，emit delta。
(c) Turn route onFinish 提取 + apply 到 playthrough_character_states。
D-03 Director 加咗 2s+ 延遲 — 玩家見到 dead time 冇任何 progress 顯示 Med UX constraint
症狀：而家每 turn 流程：用戶 click「行動」 → Director ~2s (silent) → Narrator streaming (~15-30s)。前 2s 玩家見到嘅係 client 嘅 generic「AI 諗緊...」spinner。冇任何 indication 講「Director 審視緊你嘅 action」。
後果：每 turn 比 Phase 1 baseline 慢 2 秒。10 個 turn 累積 20 秒。雖然技術上必要 (Director 必須完成先知 verdict)，但 UX-wise 用戶感受唔到呢 2 秒嘅 value，覺得「點解今次慢過上次」。
Fix（半日 UI work — UX session 一齊做）：
(a) Turn route 改 streaming server action：Director 完成嗰陣 stream 一個 marker event「✅ Director 審視完成」俾 client。
(b) Client 顯示 micro-progress：「⚖️ Director 審視中...」 → 「✍️ Narrator 寫敘事中...」。2 秒嘅 dead time 變成「Director」可見階段。
(c) Bonus：Director verdict 直接顯示俾 player (e.g.「林思雅唔接受」)，當 reject case，加強 narrative integrity 感覺。

🟢9 個 Low / Future

Rate limit edge cases 2 條
L-04 In-memory rate limit map per-serverless-instance — multi-instance race possible Low Defer
Vercel serverless 可以同時跑多個 instance。Map 喺各 instance 獨立。若用戶 quick request 落到不同 instance，rate limit 唔生效。DB UNIQUE (playthrough_id, turn_index) 仍然 catch 到 — 但用戶見到 ugly error。
Fix（Phase 3 配合 Stripe credit deduction）：用 Supabase row update + advisory lock，或者轉去 Redis。Phase 1 acceptable。
L-05 Rate limit Map 無 TTL — 內存緩慢增長 Low Defer
lastTurnAt Map 每 playthrough 加 entry，無 cleanup。Serverless instance 一般 15-30 分鐘 recycle，所以實際泄露有限。Phase 3 換 external store 自然解決。
Director quality / tuning 3 條
L-06 Director Haiku 模型可能過嚴或過鬆 — 需 empirical tuning Low User testing
Haiku 4.5 比 Sonnet 4.6 智能低少少。Director system prompt 而家係「first guess」— 未經 real 用戶 testing。可能：
• 過嚴：reject 合理 bold action (e.g. 玩家試嘢 prompt 「我衝去拯救阿明」變 reject)
• 過鬆：allow 明顯違反紅線 (e.g. 接受快速求婚)
需要 user testing 收集 cases 然後 iterate prompt。
L-07 Director failure 默默 fallback 到 allow — 紅線唔執行用戶唔知 Low Logic
若 Director call 失敗（network、API error），catch 後 fallback verdict = allow。Player 完全唔知個 turn 嘅紅線檢查 skip 咗。
Fix: 加 retry (similar to schema-gen)。If both attempts fail，console.error + emit alert metric (Sentry 將來 wire up)。
L-08 Director 用 stable prompt cache — 故事 mid-flight edit 會 stale Low Future
Anthropic cache ephemeral TTL ~5 分鐘。如果 v1.5+ 加 inline story editing，cached bible / chars 會 stale。
Phase 1 冇 editing UI，未 surface。將來加 editor 要顯式 invalidate cache (e.g. include story.updated_at in cache key)。
Skill Check edge cases 2 條
L-09 Skill check critical fail 同 regular fail 嘅 consequence_hint 一樣 Low Polish
Director 嘅 verdict 只 hint「success」/「failure」，無分 critical。skillCheckToNarratorInstruction 加咗 intensityNote 提 Narrator「critical_failure 要寫得特別慘」 — 但 consequence detail 都係 hint 嘅 hint。
Fix: Director schema 加 critical_success_consequence_hint + critical_failure_consequence_hint optional。Polish session 做。
L-10 高 skill 玩家對住低 difficulty action 永遠 critical_success — 冇驚險感 Low By design
若 skill_value = 80，difficulty = 5：d20 + 80 + 0 = 81-100，遠超 difficulty + 10 = 15 → 永遠 critical_success。
呢個係 D&D-style 設計（高 skill 應該 trivial easy action）。但 Director 應該唔好對極易嘢 require_skill_check。
Mitigation: Director prompt 已有「Skill check 只用喺真係 uncertain outcome」嘅指引。實際運作要 user testing 驗證。
Cross-call consistency 2 條
L-11 Schema gen 4 parallel calls — 字段間可能 inconsistent (e.g. bible 提林思雅但 character 叫陳家明) Low Polish
4 parallel calls 各自 see 同一 user prompt 但獨立 generate。LLM 可能 invent 不同 character name 喺 bible 同 characters array。Opening narrative 可能講「林思雅望住你」，但 characters[] 只有「陳家明」。
Fix（中等 work，~半日）：之後加 consistency pass — 用 cheap LLM 比對 4 個 output，揪出名字 / 場景 inconsistency + 自動 rewrite。Phase 1.5+ polish。
L-12 Narrator 可能引用 Director hint 字面 — system prompt 漏入 narrative Low Edge case
verdictToNarratorInstruction 有 hint string (「林思雅 should refuse because [reason]」)。理論上 well-trained Sonnet 唔會 quote 入 narrative，但 edge case 仲係可能。
Fix: Hint 加 prefix「(INTERNAL — NEVER QUOTE) ...」。Quick patch 5 分鐘可以做。
