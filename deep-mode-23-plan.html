2地基(兩個方案 + 任務都要):故事建立時宣告 game_system

同「AI 按故事決定面板」一樣 —— 故事生成時,AI 多宣告一個「呢個故事有咩 mechanic」。

擴展 schema-generator(就係我啱啱改面板嗰度),AI 喺建立故事時宣告:

  • mechanic 類型:純敘事 / 擲骰 / 回合制戰鬥 / 捕捉 …(AI 按故事內容揀,戀愛 → 純敘事、D&D → 擲骰)
  • 擲骰配置(若有):邊幾個數值算「技能」(已可由 state schema 嘅數字 field 推導)· 難度傾向
  • 任務線(③ 用):開場有咩目標

呢個宣告係聲明式、runtime-agnostic —— 唔論揀方案 A/B/C 都用得着,所以可以即刻安全咁起。

3③ 任務系統(較唔 forky · 可先行)

任務唔似擲骰有「幾時觸發」難題 —— 任務進度本質係「發生咗咩」,事後抽就啱。
故事建立 → 宣告目標(e.g.「查出走私頭目」「儲夠 1000 蚊」) → 每回合 onFinish 抽取器(現成 Haiku) 順手判斷「邊個目標推進咗 / 完成咗」 → 任務日誌 UI
  • 觸發乾淨:抽取器本身每回合都跑(抽狀態),加判任務進度 = 搭順風車,唔加新 call(留意 schema grammar · hard rule #10)。
  • 顯示:一個細任務清單(進行中 / 完成),跟 #19 —— 質性、唔好變數字 dashboard。
  • 跟故事本質:戀愛故事可以冇任務(或者軟目標),冒險故事先有明確任務線。
