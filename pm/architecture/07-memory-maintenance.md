# 07 · 記憶整理 / 清潔系統 (Memory Maintenance · 背景管家)

> 記憶系統嘅「管家」—— 定期喺背景整理、消化、清潔成個記憶宮殿。
> Anchor 原則：[01-philosophy] 原則 1 (emergent) + 原則 5 (誠實失敗)。
> 配合 [03-character-soul] (角色沉澱喺呢度發生) + [04-memory] (記憶層) 一齊睇。

---

## 核心理念

記憶處理唔應該喺玩家等緊回應嗰一刻做，應該喺背景做。

玩家撳「送出」之後等緊故事文字嗰幾秒 = 神聖時間，只可以做兩件事：① 寫故事 ② 拉返相關記憶。其他所有記憶整理工作（壓縮、消化、清潔、更新長期記憶）一律搬去背景做（玩家睇緊故事、唔等緊嘅時候）。

呢個對應業界做法：MemPalace 嘅零-LLM 寫入、Letta 嘅 sleep-time compute（背景非同步消化記憶）。

---

## 點解呢個系統存在（連住 3 件事）

呢個系統一條藤連住三個問題：

1. **解決 timeout 根因**：之前 timeout bug 嘅深層原因 = 太多嘢（摘要、lorebook 抽取、embed）塞喺玩家等緊嗰一刻做，令回合太慢。搬去背景就解決。
2. **角色靈魂沉澱**：角色嘅「沉澱消化」(見 03) 就係喺呢個背景整理位發生 —— 消化「呢幾個回合對每個角色有咩影響」、更新信念。
3. **記憶唔會無限膨脹**：定期清走垃圾、壓縮舊嘢，記憶宮殿先唔會越玩越肥、越玩越慢。

---

## 兩種清潔工作：機械式 vs 語意式

關鍵設計（向 MemPalace 學）：唔係所有清潔都要 call AI。分兩類：

| 類型 | 做咩 | 點做 | 成本 |
|---|---|---|---|
| **機械式清潔** | 刪失敗回合 · 去重複 · 清空白過場 · 合併瑣碎 entry | 純 code (regex / 規則) | 即時 · 免費 |
| **語意式消化** | 壓縮場景成摘要 · 角色情感沉澱 · 抽取信念變化 | AI (背景) | 慢 · 收費 · 但唔阻塞玩家 |

我哋而家嘅問題：**所有嘢都當語意式（每次都 call AI）**，連去重複呢類機械嘢都燒 AI 錢。MemPalace 證明好多清潔工作純 code 就做到。

## 觸發時機（沿用現有摘要機制 + 擴展）

現有摘要系統 (`lib/ai/memory/summarizer.ts`) 已經有 3 個觸發點，清潔系統 piggyback 喺同一個位：

1. **場景結束**（Director / GM 判 scene_boundary）→ 場景級整理
2. **夠 N 回合**（現時約 20）→ 區塊級整理
3. **跑到上限**（現時 25 回合）→ 強制整理

每次觸發，喺背景順手做齊：壓縮 + 消化 + 清潔。全部用 `after()` 包住（唔阻塞回應）。

---

## 清潔系統每次做嘅嘢（checklist）

背景觸發時，按順序：

1. **機械清潔（純 code · 先做 · 免費）**
   - 刪走技術失敗回合（空白 / 超時殘留 · 見原則 5）
   - 去除完全重複嘅內容
   - 清走無意義過場（純場景描寫冇推進）
2. **語意壓縮（AI · 背景）**
   - 過去場景 → 滾動摘要（已有）
3. **角色沉澱（AI · 背景 · 見 03）**
   - 評估呢幾個回合對每個 active 角色嘅影響
   - 寫經歷日誌 entry
   - 更新沉澱張力 · 檢查超 threshold → 觸發演化
   - 必要時 invalidate 角色舊信念（見 04 temporal graph）
4. **長期記憶更新（AI · 背景）**
   - Lorebook 抽取（已有）
   - 信念圖譜更新

## 同 Turn Pipeline 嘅關係

呢個系統完全活喺 [02-turn-pipeline] 個 flow 圖最底嗰個「背景 Persistence 層」入面。Turn pipeline 嘅即時部分（Narrator 寫故事）唔受影響、唔變慢。

```
玩家等緊（神聖 · 要快）：寫故事 + 拉記憶
背景（玩家睇緊 · 唔等）：清潔系統做齊上面 4 步
```

---

## 同 timeout 安全網嘅關係（原則 5）

技術失敗回合（空白 / 超時）係**機械清潔第一項要刪嘅嘢**。即係話：就算萬一有失敗回合短暫留低，清潔系統會喺下次背景整理時清走，唔會永久污染記憶。呢個係失敗安全網（原則 5）嘅後備防線。
