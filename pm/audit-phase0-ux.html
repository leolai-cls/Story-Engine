CRIT Regression · Existing Users P0B-CRIT-01
舊用戶 playthrough 鎖死喺 dropped model — 永久 403
Where
web/src/lib/billing/credits.ts:497-509 userTierAllowsModel
web/src/app/api/playthroughs/[id]/turn/route.ts:142-155 turn route tier gate
場景

Phase 0 前用戶創作咗故事 · 鎖咗 llm_model='gpt-4o' 喺 playthroughs row。 Phase 0 之後 MODELS catalog 將 GPT-4o / GPT-4o mini / Grok 2 / Grok 2 Mini / Gemini 3.1 Pro 全部 dropped。 用戶開返舊 playthrough 玩落一 turn — 

// turn route line 142-143
const playthroughModel = pt.llm_model ?? "claude-sonnet-4-6";   // = "gpt-4o"
const tierCheck = await userTierAllowsModel(supabase, user.id, playthroughModel);

// userTierAllowsModel line 496-499
const { MODELS } = await import("@/lib/ai/models");
const model = MODELS[modelId];      // = undefined (gpt-4o dropped)
if (!model) {
  return { allowed: false, tier, reason: "unknown_model" };
}

// 返到 turn route line 144 → 403 model_tier_required
SHOWSTOPPER · 任何用戶喺 Phase 0 之前揀過 GPT-4o / GPT-4o mini / Grok 2 / Grok 2 Mini / Gemini 3.1 Pro 創作嘅 playthrough · 落一 turn 即 403 「你嘅 tier (X) 唔可以用 gpt-4o」 · 叫佢「去 Settings 揀其他 model」但 Settings 已經冇 ModelPicker · 用戶冇任何 UI path 解鎖。 所有受影響 playthrough = dead state。Phase 0 ship 即引發大批 churn。
Fix：兩個層次防禦 ——
(a) userTierAllowsModel：unknown model 唔好直接 reject · check MODEL_PRICING（仲保留 dropped model entries）· 如果 pricing 存在 → 將 modelId 視為 legacy / locked playthrough · allow + log warning。
(b) Migration / cleanup job：將所有 playthroughs.llm_model 落 dropped catalog 嘅 row · re-map 去新 catalog 對應 tier 嘅 model (gpt-4o → gpt-5-4-pro · grok-2 → claude-sonnet-4-6 etc.)。先 dry-run 喺 staging 統計影響 row 數。
(c) UI safety net：turn route 嘅 403 message 唔好再叫「去 Settings 揀 model」 · 改去「升級 / contact support」 · 因為 user-facing model picker 已經冇。
Severity rationale：Phase 0 commit message 自稱「existing playthroughs use pt.llm_model (locked at creation)」 · 但冇 acknowledge userTierAllowsModel 嗰邊嘅 unknown_model 拒絕路徑會 break 呢個 locked 行為。 Locked-at-creation 假設 catalog 唔縮細 · 一縮細就玩完。

Where

場景

新用戶 click TierPicker「Standard」 · 預期：「我嘅故事會用 cheap model · 慳 credits」。 實際發生：

  1. setDefaultTier 寫入 profiles.default_tier='standard' 成功
  2. 用戶去 /stories/new 創作 → createStoryFromPrompt 讀 .select("default_model") · 完全唔讀 default_tier
  3. default_model 對新用戶係 NULL → 落 line 141 ?? DEFAULT_NARRATOR → 'claude-sonnet-4-6'
  4. Playthrough 鎖 Sonnet 4.6 · 用戶被當 Pro tier 收費 (120 credit/turn vs 預期 50)
  5. Fork story from Library 同樣問題 · forkStoryToPlaythrough 嘅 resolvedModel = params.llmModel ?? "claude-sonnet-4-6" · 完全冇查 default_tier
核心 feature 死於到貨之前 · Phase 0 唯一面向用戶嘅嘢就係 TierPicker · 但 picker 連寫入點都同 read path 唔接通。 新用戶體驗：「設定點都揀 · 故事跑乜都係一樣」 · 同時 credits 比預期燒快 2.4×。 早期 Phase 0 用戶見到 ledger 之後會 lose trust。
Fix：將 default_tier 接入創建路徑 ——
(a) createStoryFromPrompt：讀 default_tier + default_model · 行 pickModelForTier(default_tier, seedText) 攞 actual model · 用嚟 lock playthrough。 default_model 只當 legacy fallback。
(b) forkStoryToPlaythrough：caller (library/[storyId]/story-detail-actions.tsx) 唔再 hard-code Sonnet · 改為 pass 用戶 tier 經 pickModelForTier 算出 model · 或 RPC 加 p_default_tier param 由 server-side resolve。
(c) Documentation：Phase 0 commit 講「Future playthroughs created post-migration could use tier-based routing at creation time. Deferred to Phase 1」 — 但 TierPicker 已經 ship · deferred 等於 picker 完全 broken。要 unship picker（顯示 coming soon）或者連埋 (a)(b) 一齊推。
Severity rationale：呢個唔係 edge case · 係 default flow。Phase 0 commit 自認「partial」 · 但呢部分缺失就係整個 UI 改動嘅 raison d'être。揀 tier 唔影響 actual model = 用戶 trust 完全破壞。

HIGH Cost · Misleading Estimate P0B-HIGH-02
TierPicker 「~X credits / turn」 vs estimateTurnCredits 落差 2-3×
Where
web/src/components/settings/tier-picker.tsx:35-62 (creditsEstimate 字串)
web/src/lib/billing/credits.ts:283-301 estimateTurnCredits (turn route 實際用)
web/src/lib/billing/credits.ts:28-34 (docstring「honest」per-turn cost)
數字驗算
Tier (pickModelForTier 中文) TierPicker 顯示 estimateTurnCredits 實際 docstring「honest」 用邊個落帳？
Standard (GLM-5.1) ~50 ~47 48 (GLM) / 76 (Flash) 實際 token 數計（balance check 用 estimate）
Pro (Sonnet 4.6) ~120 ~76 120 同上
Pro Max (Opus 4.7) ~200 ~104 192 同上
Adult (Llama 405B) ~70 ~51 62 同上
兩個唔同 UX 結果都唔啱 ——
(1) 用戶睇 TierPicker 「~120」 · 玩落實際 balance 減 ~76 (estimateTurnCredits) · 第一感覺「咦比預期 cheaper」 · 第二感覺（睇下 ledger 用真實 token usage）「咦每 turn 真實 ~120 · 估算同 picker 一致但同 balance check 唔一致」。
(2) Free tier daily 50 credits · estimate 50 仲入嚟 OK · 但 actual 可能 76（Standard pool Flash 路徑） · 用戶第二 turn balance check 失敗 → 405「不夠 credits」。
根本問題：estimateTurnCredits 用 3K input · 但真實 turn ~15K input (Bible cache + Cards cache + 20 turns history + RAG + state) · 兩者唔同 universe。
三選一：
(a) 統一 estimateTurnCredits 用 15K input 真實 baseline · 返回真實數字 (76/120/192/62) · TierPicker 顯示同步呢個 source（最 honest · 但 pre-turn check 會 reject 更多 low-balance 用戶 → 改善 trust 但需要對齊 tier monthly credits）。
(b) TierPicker 數字改成 estimateTurnCredits 個 50/76/104/51 · 同 pre-turn check 對齊（睇起嚟更 cheap · 但 ledger 真實 token 用量會超出 estimate · 之後扣多咗 user surprise）。
(c) 加上 range「Standard ~50-80 credits / turn (visible variance) · depends on 故事長度」 · 兩邊都對。
Recommendation：(a)，配合下一步重新校準 monthly credit allocation。Founder 已喺 pricing-v2 plan 提出 v3 numbers (1K/12K/30K) · 呢度可以 sync。
Severity rationale：唔係 ship blocker 但屬於「launch 完即會收 ticket」級別。 Credits trust（CLAUDE.md hard rule #4）係 product 命脈 · 顯示同實際差 2× 會直接觸發 churn signal。
