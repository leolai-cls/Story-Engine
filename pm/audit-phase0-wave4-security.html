  2. userTierAllowsModel(supabase, user.id, 'gpt-4o-mini'):

Wave 5 fix · two-layer defense:

Layer 1 (primary · DB column lock): Migration 0022 adds BEFORE INSERT OR UPDATE trigger on playthroughs.llm_model validating it's in the union of MODELS catalog + legacy narrator allowlist. Hard fail at DB layer · no upstream change can bypass.

create or replace function public.protect_playthrough_llm_model()
returns trigger language plpgsql security invoker as $$
declare
  v_allowed text[] := ARRAY[
    -- Current MODELS catalog (sync to lib/ai/models.ts)
    'claude-haiku-4-5','claude-sonnet-4-6','claude-opus-4-7',
    'gpt-5-4-pro','gemini-3-5-flash','glm-5-1','llama-3-1-405b-uncensored',
    -- LEGACY_NARRATORS (sync to lib/billing/credits.ts)
    'gpt-4o','gpt-4o-mini','gemini-3-1-pro','grok-2','grok-2-mini'
  ];
begin
  if NEW.llm_model is not null and not (NEW.llm_model = any(v_allowed)) then
    raise exception 'invalid_llm_model: %', NEW.llm_model using errcode = '23514';
  end if;
  -- Also: prevent UPDATE from changing llm_model except via service role
  -- (back-compat: tier downgrade migration / refunds need the path).
  if TG_OP = 'UPDATE' and OLD.llm_model is not null
     and OLD.llm_model is distinct from NEW.llm_model
     and auth.role() <> 'service_role' then
    raise exception 'llm_model_immutable_post_creation' using errcode = '42501';
  end if;
  return NEW;
end;
$$;

create trigger playthroughs_protect_llm_model
before insert or update on public.playthroughs
for each row execute function public.protect_playthrough_llm_model();

This fallback is the load-bearing piece of the credit-arbitrage attack: unknown id → Sonnet narrator + cheap bill. The comment says "Schema enforces this elsewhere" — Wave 4 shows the schema enforcement is NOT comprehensive (no DB constraint · no Server Action validation · only userTierAllowsModel's allowlist · which itself allows the cheap ids via LEGACY_NARRATORS).

This is the structural-flaw question the prompt asked about: "is there a deeper architectural flaw that should be addressed?" Answer: yes · this single line. Three consecutive waves have been narrowing the symptom · the root cause is the silent fallback. Until it's promoted to throw (or returns a sentinel that turn route handles · 503 "model misconfigured") · every new model addition to MODEL_PRICING reopens the same attack vector. The "5 minutes to fix one channel · 1 day to play whack-a-mole forever" trade-off favors fixing the root.

Wave 5 or Phase 1 polish: change providers.ts to throw new Error('unknown_model · ' + id). Turn route already has its own validation (userTierAllowsModel) so this branch should be unreachable in practice. Add a metric/alert to surface if it IS reached (= data corruption · investigate).

Trade-off: a user with a corrupted pt.llm_model gets a 500 instead of a silent Sonnet rescue. But corruption is the rare case · arbitrage is the actual attack. The current trade-off favors the rare case · we should flip it.

Not blocking Wave 5 ship · since the DB trigger from CRIT-01 fix already closes the channel. But strongly recommend including as part of the same fix wave for completeness.
