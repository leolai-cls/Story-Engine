2 · Findings · Low / Info Only

LOW / INFO P0AW5-INFO-01 Trigger service_role detection uses legacy GUC form (latent, not exploitable)

Where: supabase/migrations/0022_phase0_lock_llm_model_postcreate.sql:35

Observation: The trigger reads current_setting('request.jwt.claim.role', true) (singular claim, per-key GUC), but the rest of this codebase consistently uses current_setting('request.jwt.claims', true)::jsonb->>'role' (plural claims, full JSON GUC) — see migrations 0002:150 and 0007:56, plus auth.role() in 0010/0011/0012/0013/0014. The singular form is a legacy PostgREST 7.x convention; current Supabase populates the plural form.

Why no impact on the closed attack vector: the trigger has 3 OR-bypass conditions:

  1. request.jwt.claim.role = 'service_role' ← possibly stale GUC name
  2. current_user = 'service_role'
  3. current_user = 'postgres'

For an authenticated browser user, current_user is authenticated, so #2 and #3 cannot match; #1 also fails because the user is not service_role regardless of which GUC form is used. The attack vector is fully blocked. Wave 4's security goal stands.

Latent concern: for legitimate service_role webhooks/backfills calling via PostgREST, current_user is also authenticated (PostgREST switches role from JWT). The intended bypass relies on #1 — which may not match if the singular GUC form isn't populated by current Supabase. Today this is harmless because no code path actually updates llm_model post-create (grep across web/src shows zero hits for .update({llm_model}) on playthroughs). If a future admin script needs to rewrite locked-model values, it would fail with a confusing error.

Recommendation: not a ship blocker. Tracker-only. When/if an admin backfill is added, swap the trigger to use the same pattern as 0002/0007: coalesce(current_setting('request.jwt.claims', true)::jsonb->>'role', '') = 'service_role' OR equivalently auth.role() = 'service_role' per 0010+ convention. Decision: ACCEPT for Phase 0 close · log to pm/BACKLOG.md.
