🧠 Memory architecture v2

記憶系統重新設計 · MemPalace pattern

借 MemPalace 嘅 hierarchical namespace + knowledge graph + hybrid retrieval 模式 · 重做 4 層記憶 · 一邊慳成本 一邊提升「AI 真係記得」嘅 UX。

🎯 一頁總結
而家：4 層記憶 · 每 turn 全部 dump 入 LLM · ~14,000 tokens · noise 多 · 50% irrelevant
v2：分 namespace (Wings → Rooms → Drawers) · scoped retrieval · keyword + temporal boost · knowledge graph for NPC 關係
結果：~7,000 tokens per turn (−50%) · 精準度 ↑ · 故事一致性 ↑ · cost ↓ 40-50%
UX win：用戶感受到「真係記得 NPC X 細節」· 唔再要 dump 全本 history
商業 win：$19.99 Legend 由 250 Sonnet turns → ~500 turns · 對標 Claude Pro 嘅 800-1600

📦而家 4 層記憶 (現況)

每 turn 全部 always-load · 唔分 relevance · noise 大 cost 高

1 Last 20 turns 全文 ~10,000 tokens ALWAYS
2 Rolling summary (lossy) ~500 tokens ALWAYS · LOSSY
3 RAG top-3 chunks (冇 similarity floor) ~600 tokens ALWAYS · NOISE
4 Lorebook (全部 active entries) ~500 tokens ALWAYS
+ Bible + Character Cards (Anthropic cached) ~2,600 cached OK
Per turn input → Narrator ~14,200 tokens · ~$0.060 / Sonnet turn

🏛️MemPalace pattern → Story Engine map

借 MemPalace 嘅組織方式 · 改造我哋 4 層

MemPalace conceptStory Engine 對應應用
Wings (人 / project) Playthrough · NPC · Quest line 頂層 namespace
Rooms (主題) Scene (location) · NPC interaction · Quest milestone Mid-level grouping · scoped retrieval
Drawers (verbatim) Turn texts · NPC dialogue · player decisions 原文存 · 唔 summarize lossy
Knowledge graph NPC ↔ Item ↔ Location ↔ Event relationships Replace flat lorebook
Hybrid pipeline Semantic + keyword + temporal boosting Replace pure top-K
Scoped query 「Search 阿明 room」唔係「Search 成個 playthrough」 大幅減 noise
MemPalace benchmark: 96.6% R@5 on LongMemEval · 唔需要 LLM reranking · 純 structured retrieval 已贏 flat RAG 一截。Story Engine 抄呢個 architecture · 預期 retrieval 精準度提升 1.5-2×。

🗂️新 schema (Supabase pgvector + SQL)

改 memory_chunks 表結構 · 加 namespace · 加 knowledge graph 表

-- Migration 0019: hierarchical memory namespace (MemPalace pattern) -- Wings = playthrough_id (already in PK) -- Rooms = NEW: room_kind + room_id (scoped grouping) -- Drawers = chunk text (existing) alter table memory_chunks add column room_kind text -- 'scene' | 'npc' | 'quest' | 'world' check (room_kind in ('scene', 'npc', 'quest', 'world')); alter table memory_chunks add column room_id text; -- 'forest_edge' or 'npc:阿明' or 'main_quest' create index idx_memory_chunks_scoped on memory_chunks (playthrough_id, room_kind, room_id); -- Knowledge graph: nodes + edges (relationships between entities) create table mem_nodes ( id uuid primary key default gen_random_uuid(), playthrough_id uuid references playthroughs on delete cascade, kind text, -- 'npc' | 'item' | 'location' | 'event' label text, -- '阿明' | '咖啡店' | '玩家攻擊狼' attrs jsonb, -- 4-axis disposition / item stats / scene weather created_at timestamptz default now() ); create table mem_edges ( id uuid primary key default gen_random_uuid(), playthrough_id uuid references playthroughs on delete cascade, src_node_id uuid references mem_nodes on delete cascade, dst_node_id uuid references mem_nodes on delete cascade, relation text, -- 'knows' | 'owns' | 'happened_at' | 'trusts:60' weight numeric default 1.0, evidence_turn_idx int -- source turn for this relationship );
Zero downtime：新 columns + tables 都係 additive · 舊 chunks 用 default room_kind='world' backfill · existing reads 繼續 work。

🚀新 retrieval pipeline

由 Director 揀 rooms · scoped RAG + keyword + temporal + graph 一齊 hybrid

🎬
1. Director picks rooms
Director (Haiku) 分析用戶輸入 + state · output: rooms_to_load: ["npc:阿明", "scene:咖啡店"]
🔍
2. Scoped vector search
pgvector WHERE room_kind='npc' AND room_id='阿明' · top-3 · similarity floor 0.55
🔑
3. Keyword boost
User input 內提到嘅 entity name (e.g. 「阿明」「咖啡店」) → bump 對應 chunks score
⏰
4. Temporal boost
最近 5 turns 嘅 chunks · weight × 1.5 · 早 turn × 0.8
🕸️
5. Graph traversal
Knowledge graph 揾 active entities 嘅 1-hop neighbors · 加入 context
📦
6. Compose narrator context
~7,000 tokens verbatim · scoped · relevant · 比之前 14,200 慳一半
